# shipit-slice
Takes one slice from its build plan to a pull request that is ready to ship. The lead runs it in the way the owner chose (`shipit-roadmap`, How slices run). With one session per slice, the lead or the owner runs steps 1 and 2 in the main working copy, and the owner then opens a new session in the worktree, which runs the rest; in every other way the steps after step 2 run in the lead's session. The slice agent (`shipit:slice`) may run step 1 for the lead. Terms: [vocabulary](../../docs/vocab.md).
## Inputs
- The slice (the argument) and its goal: from `shipit status`.
- The roadmap, the slice's entry in it, the goal and the build plan if it exists: from the store (Store files).
- The setup (`.config/shipit.toml`) and the domain pack, for ranks, caps and what a check is.
- The machine facts and notes: `shipit doctor`.
## Output
The pull request body, which has no form: `shipit status --summary <slice>`, then the merged review's Reading path with its diagrams, Other files and Look here, then the slice's Verified, Inferred and Unverifiable lists.
## Effects
Writes the build plan and its `plan-review` into the store with `shipit store put`, drafting in a drafts folder that it makes itself with `mkdir -p .shipit/td/<slice>` and the one line `*` in its `.gitignore`, so that git ignores it; runs `shipit validate`, `shipit receipt`, `shipit check`, `shipit log` and `shipit doctor`; starts `shipit:scout`, `shipit:plan-reviewer`, `shipit:maker` and `shipit:tester`, and the reviewers through `shipit-review`; starts the slice in step 2; for one session per slice, works in a worktree (`git worktree add`); the makers it starts commit on the slice branch (an isolated maker runs `git switch slice/<goal>/<slice>` and `shipit pre-commit`, and the lead frees its worktree with `git worktree list`, `git worktree remove .claude/worktrees/agent-<id>` and `git branch -d worktree-agent-<id>`; a slice over the cap is carried onto new parts with `git checkout slice/<goal>/<old-slice> -- <paths>`); pushes the slice branch (`git push -u origin slice/<goal>/<slice>`); opens the pull request (`gh pr create`); sends one message to the lead.
Questions to the owner use the words of the [guide](../../docs/guide.md) and its glossary, and ask only what changes what is built.
Never: merge, tag, push another branch, change the setup, or review its own work as the lead. As a slice agent: ask the owner directly.
## Outcomes
- **ready to ship**: `shipit status` says so, the branch is pushed and the pull request is open. Next: one message to the lead (as a slice agent, its final message); the owner reads the pull request and ships; after the merge the lead runs `shipit log <slice> shipped --merge <commit>`.
- **blocked**: only the owner can settle a question. Next: a decision point for the owner; message the lead "blocked" (as a slice agent, end with the decision point in the final message); the lead asks the owner and starts a new slice agent.
- **fix rounds used up**: past `agents.max_fix_rounds` a finding is still open. Next: the lead rules and records it with `shipit log <slice> note`; each open must-fix becomes `shipit log <slice> known-issue`; then ready to ship, with known issues.
- **no pull request host**: `gh` is missing or has no host for this repository. Next: the branch is pushed; tell the owner where it is; the owner opens the pull request.
## Steps
1. Build plan. The planner fills `build-plan` as a draft in a drafts folder that you make yourself with `mkdir -p .shipit/td/<slice>`, never asking the owner for one (`shipit template build-plan`); check it with `shipit validate build-plan <draft>`. Start `shipit:plan-reviewer` at the top tier, at the planner's effort, to fill `plan-review` (`shipit template plan-review`); run fix rounds; put the approved build plan and the `plan-review` that approved it into the store (Store files); record `shipit receipt plan-review <slice>`.
   - Background facts: start `shipit:scout` (`shipit template scout-report`). On `partial` or `not-found` ask once more with a narrower question and say where it looked (`agents.roles.scout.retries`); then use a scout at `agents.roles.scout.escalate_to`; then read the source yourself. Log each step with `shipit log <slice> note`.
   - Owner questions: each is a `decision-point` (`shipit template decision-point`) with a ```` ```example ```` block where it helps the owner decide (a command, a sample output, two lines of the change); check it with `shipit validate decision-point <file>`.
2. Only now, with the approved build plan in the store, run `shipit start <slice>`; it refuses at the cap or before the slices it comes `after` have shipped: report and stop. For one session per slice, make the worktree as `shipit start` prints it, at the absolute path `.shipit/wt/<slice>` under the top of the main working copy: `git worktree add <path> slice/<goal>/<slice>`; `shipit start` keeps `.shipit/wt/` out of git. The slice session is named by `shipit session-name <goal> <slice>`. Then stop and tell the owner: the owner opens a new session in the worktree (started in the path above, named by `shipit session-name <goal> <slice>`), and it continues from step 3, as `shipit status` shows. In every other way make no worktree: git refuses a branch that two worktrees hold. Go on from step 3 in this session.
3. Make: start `shipit:maker` one build-plan step at a time, following the skill pack's make phase (`packs.skill`), each with the model and effort of `agents.roles.maker`; no review between steps. Use what the machine has; for a missing tool follow the recipe of the machine notes (`shipit doctor` shows it); never install globally. The maker commits the coverage map. Start each maker where the slice is made: in a slice session (one session per slice) it is the session's folder; in every other way it is an isolated maker (the first bullets). A lead agent never edits or commits the work, so that a receipt names who made it: this is a rule of the process, and the tool does not check it. Each maker report ends with Verified, Inferred and Unverifiable.
   - Start it with `isolation: "worktree"`, `run_in_background: true`, and the prompt's first line `shipit-branch: slice/<goal>/<slice>`.
   - Its first command is `git switch slice/<goal>/<slice>`; if git refuses, it reports and stops.
   - Then it runs `shipit pre-commit`; on a `not checked` line, it waits a few seconds and runs it once more (the launch is recorded a moment after the agent is up), and reports and stops if the line comes again.
   - The step that ends the slice's making runs `shipit check` in its worktree.
   - After a `shipit:maker` ends, the lead runs `git worktree list` and frees its worktree with `git worktree remove .claude/worktrees/agent-<id>` and `git branch -d worktree-agent-<id>`, each alone in its call, before the next maker of that slice starts.
   - Start a new `shipit:maker` for each step: never resume an isolated maker, because a resumed agent works outside its worktree, where the commit hook cannot see it.
   - A bug fix: the build plan names a test that reproduces the bug as its first step, and `shipit:maker` commits that test alone, failing, before any fix; the fix comes in later commits.
   - The lead checks it before the reviews: in a scratch worktree of the test's commit (`git worktree add --detach <dir> <commit>`) the named test fails, and at the slice's last commit it passes; both runs go under Verified, and a missing test, or one that passes before the fix, is a must-fix finding.
   - The cap: the `shipit:maker` counts the changed files after each step with `git diff --shortstat <base>...HEAD` and stops at about 80% of `gate.max_files`, reporting before it writes more. A slice that `shipit check` refuses for size stops: the branch is kept, nothing is pushed or reviewed, and the planner splits the real diff into releasable slices (each complete, tested, under the cap, ordered by `after`) as a new roadmap version for the owner. Each part branches from the base, and its maker carries its files over with `git checkout slice/<goal>/<old-slice> -- <paths>`, completes and checks it; a later part starts after the earlier ones merge; the old branch is deleted, with the owner's ok, once the last part ships.
4. Run `shipit check` until it passes. In a slice session the session runs it; in every other way the isolated maker's last step has run it in its worktree, and the receipt, keyed by the tree, is seen from every working copy: read it with `shipit status`. This is not a fix round. Never remove, skip or loosen a test to make a check pass; a changed test goes to the reviewers with its reason.
5. Run `shipit-review` in slice mode: the full review (reader, informed review, second opinion) for every slice in v1. If the roadmap marks a test drive: prepare the folder as the domain pack says, start `shipit:tester` with `shipit-test-drive` and the line `shipit-branch: slice/<goal>/<slice>`, check the report with `shipit validate test-drive <file>`, and record `shipit receipt test-drive <slice>`. The test drive runs after the reviews approve, because its receipt is keyed by the tree.
6. Fix rounds, at most `agents.max_fix_rounds`: fix, run `shipit check`, review again (receipts are keyed by the change). If the roadmap marks a test drive, run it again after the reviews approve: its receipt is keyed by the tree, so each fix round needs a new one, at most `agents.max_fix_rounds` times. Log each owner answer with `shipit log <slice> answer --finding <Fn> --kind <kind> --by <model>:<effort> --text <answer>`: `--kind` is the receipt kind of the finding, `--by` is the lead's own model and effort, and `--text` names the owner (`--by owner` is refused: a known tool gap). Past the cap the lead rules and writes known issues.
7. When `shipit status` says "ready to ship": push the branch with `git push -u origin slice/<goal>/<slice>`, alone in its call, the branch typed out in full: no variable, no `&&`, no command substitution. Write the body to a file in a drafts folder made with `mkdir -p .shipit/td/<slice>`, which git ignores: `shipit status --summary <slice>`, then the merged review's Reading path, diagrams, Other files and Look here, then Verified (each done-when item with the test the coverage record shows ran, and the check receipt), Inferred (what the owner must still check) and Unverifiable. Then run `gh pr create --title <title> --body-file <file>`. If gh is missing: stop as **no pull request host**.
8. One message to the lead, within `owner.status_update_max_lines`: ready to ship or blocked, the pull request, the number of known issues and how many claims are inferred. Message the lead session by its name (`shipit session-name <goal>`); the lead confirms with `shipit status`.
## As a slice agent
- The lead starts `shipit:slice` in the main working copy, at the planner's rank, and passes the goal, the slice and the store path. The agent runs step 1 and ends; the lead runs the rest in the way the owner chose.
- It never starts `shipit:maker`: the lead does.
- Its scout and the reviewer of the build plan run one layer deeper, each with the model and effort of its rank. None of them can start an agent: their `tools` leave `Agent` out. The review gate and the agent cap count agents started by an agent (measured); `docs/claude-code.md` says what that means for `agents.parallel.agents`.
- It never asks the owner. A decision point ends it as **blocked**, and its final message carries the decision point; the lead asks the owner and starts a new slice agent, which continues from `shipit status`.
- Its final message is one line: the build plan is approved, or blocked; it ends with Verified, Inferred and Unverifiable.
## Store files
- The store is `<git common dir>/shipit`. Find it with `git rev-parse --git-common-dir`, run alone, and type the printed path into the next command. A skill never spells the git folder itself.
- Write: draft with the file tools in a drafts folder made with `mkdir -p .shipit/td/<slice>`, validate the draft there, then put it in: `shipit store put build-plan <draft> --goal <goal> --slice <slice>`, then `shipit store put plan-review <draft> --goal <goal> --slice <slice>`. It checks the draft again, writes it at its place and prints the path. Until the slice is started a put replaces the build plan or the `plan-review`; after that it refuses, and a changed build plan is the lead's copy by hand (docs/store.md). A store file is never edited in place.
- Read: `shipit store show <kind> --goal <goal> [--slice <slice>] [--round <k>] --copy`, from any working copy, then the Read tool on the path it prints.
- If `shipit store put` refuses, report its message and stop.
